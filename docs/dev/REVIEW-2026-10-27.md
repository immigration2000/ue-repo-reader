# A1 코드 분석 — 2026-10-27 · codex

분석 기준: `1e1018e` (F8 완료). 실행 코드 수정 없이 구조, 오류 처리, 회귀 테스트와 첫 실행을 점검했다.
외부 제품/엔진 문서의 최신성이나 모든 UE 직렬화 형식을 검증한 리뷰는 아니다.

## 전체 판단

에디터 없이 UE 프로젝트의 저장된 실행 흐름과 데이터를 AI가 읽게 만드는 목적에 잘 맞는다.
BP 실행/데이터 흐름, 맵 인스턴스, 데이터 에셋을 함께 읽고 서로 연결하는 것이 핵심 장점이다.
현재 우선순위는 새 에셋 종류보다 입력 보존, 최초 설치 안정성, 부분 실패 보고를 보강하는 것이다.
`노드 N/N`은 핀을 읽은 노드 수의 지표이며, 모든 속성과 렌더링 의미가 정확하다는 보증은 아니다.

## 실행 구조

1. `scripts/ue_repo_digest.py`: URL/로컬 경로 → 부분 클론·LFS 선택 다운로드 → 프로젝트·플러그인 Content 마운트 수집.
2. 패키지 헤더로 에셋 클래스를 분류하고 C++ 헤더의 리플렉션 선언을 정규식으로 색인한다.
3. `spawn` 프로세스 풀이 BP, 데이터, 맵을 순서대로 병렬 처리한다.
4. `bp_reader.py`: 고정 파서 설치와 호환성 패치 → 버전별 핀 포맷 탐색 → 실행 흐름/순수 식/애님 상태 머신 렌더링.
5. `data_reader.py`: 자체 `TaggedReader`로 중첩 프로퍼티와 네이티브 페이로드를 읽고 종류별로 렌더링한다.
6. `map_reader.py`: 레벨 BP, 배치 액터, World Partition 외부 액터와 인스턴스 저장값을 합친다.
7. 데이터 사용처, 배치 맵, 입력 매핑, GameplayTags를 교차 검사하고 INDEX·Markdown·digest.json을 쓴다.
8. `server/server.py`: 같은 CLI를 서브프로세스로 호출하고 작업 큐·캐시·페이지 단위 읽기/검색을 MCP로 제공한다.

장점은 리더별 역할 분리, 표준 라이브러리 중심 구성, 고정 커밋 회귀, 알 수 없는 포맷에 대한 경고다.
반면 `bp_reader.py`가 설치·전역 패치·버전 선택·렌더링을 함께 맡고, 전역 `_FIELDS`, `_TEXT`, 현재 Ctx에 의존한다.
지금의 프로세스별 순차 파싱 전제를 유지하거나, 향후 분리 시 이 상태를 명시적으로 전달해야 한다.
C++ 정규식 색인과 짧은 에셋 이름 기반 교차 참조는 탐색용이며 정밀한 전체 의존성 그래프로 취급하면 안 된다.

## 확인한 문제와 수정 방향

### A2 · P1 · 출력 경로가 입력과 겹치면 프로젝트 삭제 가능

`ue_repo_digest.py:1052–1054`는 기존 `--out` 폴더를 무조건 `shutil.rmtree`한다.
입력과 출력이 같은지, 출력이 입력의 상위인지 검증하지 않는다. `source=X --out=X`는 원본 삭제 경로에 들어간다.
실제 저장소에서는 삭제 함수를 모킹해 호출 대상이 입력 루트임을 확인했다. 사용자 프로젝트를 삭제하지 않았다.
일회용 폴더에서도 원본 파일 삭제 후 렌더 단계까지 진행하는 것을 확인했으나, 마지막 쓰기는 디스크 부족으로 실패했다.

수정 방향: 경로를 resolve해 입력과 같거나 입력을 포함하는 출력을 거부한다. 프로젝트 선택/옵션 검증도 삭제보다 먼저 한다.
기존 출력 교체는 도구가 생성한 디렉터리임을 확인하고, 가능하면 임시 출력 생성 후 교체한다.

### A3 · P1 · 최초 파서 설치 시 워커끼리 Git 경합

`bp_reader.py:32–48`의 설치 함수는 공용 캐시에 잠금 없이 init/fetch/checkout한다.
`ue_repo_digest.py:437–488`에서 모든 워커 초기화가 이 함수를 호출하므로, 빈 캐시에서는 같은 Git 저장소를 동시에 수정한다.
첫 회귀 실행의 ves 로그에서 config/shallow 잠금 및 템플릿 파일 충돌이 나고, BP 2개 중 1개가 실패했다.
캐시가 만들어진 뒤에는 같은 픽스처가 통과했다.

수정 방향: 부모에서 설치를 완료한 뒤 Pool을 생성한다. 별도 CLI 동시 실행도 고려해 임시 디렉터리와 설치 잠금을 둔다.
합성 핀 테스트와 별도로 빈 캐시 부트스트랩 테스트가 필요하다.

### A4 · P1 · 부분 실패가 INDEX의 성공 판정에서 빠짐

`map_reader.py:89–96`는 속성 실패를 빈 dict로 바꾼다. 외부 액터 실패 수와 레벨 BP 예외도 summary의 오류로 전달하지 않는다.
특히 레벨 BP 예외는 `level_bp_nodes=(0,0)`으로 바뀌어 정상적인 빈 레벨 BP와 구별되지 않는다.
`ue_repo_digest.py:982–1004`의 성공 판정은 이 상태를 확인하지 않는다.

레벨 BP·외부 액터 실패를 주입한 검사에서 맵 문서에는 실패가 있었지만 INDEX에는 `everything decoded cleanly`가 나왔다.
`tests/regress.py:51–82`도 이 INDEX를 통과시켰다. BP 수·핀 수와 선택된 문자열만 검사하고 데이터/맵 실패 수는 직접 검증하지 않는다.
BP 그래프 렌더링 예외도 `bp_reader.py:1915`에서 문서 문자열로만 바뀌므로 summary 오류 전파 대상에 포함해야 한다.

수정 방향: 종류별 구조화된 오류/부분 성공 필드를 반환하고 INDEX·digest.json·회귀 검사가 같은 필드를 사용하게 한다.
잘 읽지 못한 기본값과 실제 클래스 기본값을 구별한다.

### A5 · P2 · 조용한 MCP 작업에 제한시간이 적용되지 않음

`server.py:183–192`는 stdout의 다음 줄을 기다리는 루프 안에서만 deadline을 확인한다.
자식이 출력 없이 멈추면 검사에 도달하지 않아 단일 RUN_SLOT을 계속 점유할 수 있다.
해당 함수를 추출해 stdout 없는 자식 프로세스로 검사했다. 제한 0.1초, 실행 약 0.53초인데 상태가 `done`이었다.

수정 방향: 출력 수집과 timeout 감시를 분리하고, 시간 초과 시 자식 종료와 wait를 보장한다. 자식 워커 정리도 함께 확인한다.

### H7 · P2 · Windows 회귀 러너 stdout 인코딩

기본 실행은 `tests/regress.py:106`의 em dash 출력에서 `UnicodeEncodeError: cp949`로 중단됐다.
CLI 본체는 UTF-8을 설정하지만 회귀 러너에는 같은 처리가 없다.
`PYTHONIOENCODING=utf-8:replace`를 지정한 재실행은 통과했다. PowerShell 5.1 자체를 시험한 결과는 아니다.
이 PC의 `python`은 WindowsApps 바로가기여서 앱 번들의 실제 Python 3.12.14를 사용했다.

### A6 · P2 · MCP 캐시 키가 도구 버전과 프로젝트 식별을 충분히 반영하지 않음

`server.py:155–159`의 키에는 도구/출력 버전이 없다. 파서를 바꾸고 기존 DATA를 재사용하면 같은 커밋의 예전 digest가 계속 반환된다.
또 프로젝트 경로를 치환·40자 절단하므로 `Chapters/One`과 `Chapters-One`도 같은 키가 된다(함수 호출로 확인).

수정 방향: 도구/출력 스키마 버전과 전체 프로젝트 식별자의 해시를 키에 넣는다.
기존 캐시가 있으면 생성 버전을 검사한다.
